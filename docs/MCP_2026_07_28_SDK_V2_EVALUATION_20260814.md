# YangTools MCP 2026-07-28 / Python SDK v2 评估

日期：2026-08-14

## 当前实现

- `McpServer/requirements.txt` 当前固定为 `mcp>=1.2.0,<2`，即 Python MCP SDK v1 维护线。
- `McpServer/server.py` 使用 `from mcp.server.fastmcp import FastMCP`，通过 stdio 向 Codex/Claude 等 MCP Host 暴露工具。
- Python MCP Server 再通过本机动态端口 + bearer token 调用 Revit 内部 `McpGateway`。
- C# Revit 网关不是标准 MCP Host-facing transport，而是 YangTools 内部桥接 HTTP API，因此升级 Python MCP SDK 不要求重写 Revit ExternalEvent/主线程执行架构。

## 名称澄清

“JSON-RPC 2.0”不是新的 MCP 2.0；MCP 一直使用 JSON-RPC 2.0。官方 MCP 规范采用日期版本。2026-08-14 时最新正式规范为 `2026-07-28`；官方 Python SDK 当前稳定主线为 v2。

## 对 YangTools 有价值的变化

1. Python SDK v2 是当前稳定主线，并支持 `2026-07-28` 及更早规范。
2. 高层类由 `FastMCP` 改为 `MCPServer`，SDK 内部架构和类型验证更严格。
3. `2026-07-28` 规范核心改为无会话/无 handshake 的 stateless request-response；对远程 HTTP MCP 扩展价值大，对当前本机 stdio 桥接收益较小。
4. Multi Round-Trip Requests 可让工具在一次工作流中向用户补问参数/确认后继续，未来适合 Revit 高风险写操作确认。
5. tools/resources 列表结果支持缓存提示；YangTools 当前工具数量少，收益有限。
6. Header-based routing、授权强化主要面向远程 Streamable HTTP/网关部署；YangTools 当前本机 stdio + loopback bearer token 不急需。
7. SDK v2 对输入/输出协议类型校验更严格，有利于尽早发现不合规 MCP 返回。

## 当前决定

本轮**不顺带迁移 MCP SDK v2**。原因：用户本轮明确要求的是退役助手数据清理，同时现有 MCP v1 stdio 桥接已经可用。SDK v2 有 breaking changes，应作为独立任务迁移和回归，避免与 Revit 功能改动混在一起。

后续若升级，建议单独执行：

- `requirements.txt`: `mcp>=2,<3`；
- `FastMCP` → `MCPServer`；
- 保持 stdio transport；
- 将当前 JSON 字符串返回逐步改为 structured output；
- 用实际 MCP Host 测试 `tools/list`、全部 tool call、异常、超时、Revit 未启动/多实例发现；
- Revit C# Gateway 与 ExternalEvent 主线程执行模型不因 SDK v2 而重写。


## 用户最终决定（2026-08-14）

- MCP SDK v2 / MCP `2026-07-28` **只记录为后续独立技术债/升级任务**。
- 当前 YangTools 不迁移 SDK，不改 `requirements.txt`，不改 `FastMCP` 服务入口，不重写 Revit C# Gateway。
- 后续只有用户明确提出“升级 MCP”时，才单独开任务执行迁移、Host 兼容测试和全部 Tool 回归。
