# 重复项目参数清理 3.1.33

## 实机诊断结论

测试模型：Revit 2021，项目参数 2750 个，唯一名称 978 个，重复名称 606 组。
按参数清单计算，若每组保留 1 个参数，理论来源参数数量为 1772 个。

回滚实验：

| 方案 | 10 个来源参数耗时 | 结果 |
|---|---:|---|
| 直接 Document.Delete | 99.9 ms | 删除 10/10 |
| BindingMap.Remove | 95.5 ms | 实际移除 0，来源已处于不可匹配/孤立状态 |
| Remove + Delete | 119.2 ms | 比直接 Delete 慢 19% |

结论：不增加解绑步骤，继续直接删除来源 ParameterElement。

## 3.1.32 卡顿根因

Revit 对每个来源 ParameterElement 返回两个实际删除 ID：

1. ParameterElement 自身；
2. 一个随父参数删除的依赖子对象。

旧版把第二个 ID 无条件判定为危险级联，执行：

```text
批次 Delete
→ 发现额外 ID
→ 回滚
→ 二分
→ 单项 Delete
→ 仍发现额外 ID
→ 回滚并阻止
```

因此 Delete API 自身只有约 100 ms，但工具会产生大量重复 Delete、回滚和二分。

## 新删除算法

删除前对每个来源 ParameterElement 调用：

```csharp
record.Element.GetDependentElements(null)
```

建立允许删除集合：

```text
请求删除的来源 ParameterElement ID
+
Revit 预先报告的依赖子对象 ID
```

执行批量 `Document.Delete` 后：

- 请求参数全部被删除，且返回 ID 全部属于允许集合：提交批次；
- 返回未预期 ID，或请求参数缺失：回滚并二分定位；
- 单个异常参数只阻止自身，不影响其他批次。

已知的明细表、视图过滤器、全局参数、共享参数和参数值冲突保护仍在删除候选筛选阶段执行。

## 性能结构

- 默认批次：250。
- 606 个正常候选：纯逻辑模拟为 3 个初始批次。
- 当前模型理论 1772 个来源：约 8 个初始批次。
- 异常参数只在所属批次内二分。
- 不使用 `BindingMap.Remove`。
- 不进行逐参数 Collector 扫描。

## 全链路去重

快速处理现在只执行一次提交前完整扫描：

```text
快照
→ 合并绑定和值
→ 批量删除
→ 提交前扫描
→ 参数值和唯一性复核
→ TransactionGroup 提交
→ 写报告
→ 复用提交前扫描结果刷新 UI
```

已删除：

- 事务内写 CSV；
- 提交后的第二次完整扫描；
- 第二次引用扫描；
- 第二次 606 行列表重建前的数据扫描。

## 仍保留的数据原则

1. 保留现有原参数，不进行全部删除重建。
2. 实例元素与元素类型各单次遍历。
3. 按 ParameterElement ID 识别参数，不使用同名 LookupParameter。
4. Double、Integer、String、ElementId 使用内部值直接读取和 Set。
5. `AsValueString()` 只用于报告显示，不能参与回填。
6. 清理前不同非空内部值必须在清理后全部存在。
7. 已报告完整删除的组，清理后必须只剩一个 ParameterElement。
8. 复核失败时回滚整个 TransactionGroup。

## 实机复测要求

先使用“测试：最多 10 个来源参数”，检查运行输出：

```text
删除性能：Delete API ... ms
批量尝试 1
成功批次 1
二分 0
单项定位 0
回滚 0
依赖检查：允许的 Revit 子对象约 10 个
```

同时必须满足：

- 元素参数值：通过；
- 已完成删除组唯一性：通过；
- 清理后的选中参数名称各剩 1 个；
- Revit 撤销后参数和值恢复。
